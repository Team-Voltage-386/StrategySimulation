Four labs: observe, explain, measure, verify

These are not click-through tutorials. Each lab asks you to make a prediction, gather reproducible evidence, and explain what the simulator did. Work in pairs when possible: one student operates the app while the other keeps the lab record.

Do the labs in order the first time. The screenshots are generated from the live UI, so each cyan callout marks only the next control to use. The tab handbooks cover the rest of the UI in full.

00Before you begin

The lab rule

Predict before you run. A good lab record has four headings: prediction, setup, result, and what I would test next. Record strategy names, seeds, repetitions, and every setting you changed. “It looked better” is an observation; it is not yet a result.

  1. Launch the app with run.bat. On the MATCH tab, confirm that the field, roster, and transport bar are visible.
  2. Keep the generated tab handbooks nearby. They explain every numbered control in depth; these labs tell you what to do with those controls and what evidence to collect.
  3. Use a fresh text file or notebook page per lab. Do not overwrite an example strategy; copy it under a new, descriptive filename first.

01Trace one CORAL cycle

Question: How does one line in a strategy file become a score on the field?

Steps

  1. In the roster/settings panel, set PRIMARY to AI-driven and choose cycle_coral. Click RESET after changing either value; staged roster and strategy changes do not alter the match already on the field.
  2. Click play. Watch until PRIMARY collects a CORAL, travels toward the REEF, and deposits. Pause immediately after the score/event appears. Write down the match time, score, and whether the deposit succeeded or missed.
  3. Drag the transport slider back to just before pickup, then advance through pickup and deposit. Describe three visible state changes: loose piece, held piece, and scored or released piece.
  4. Open game_specific/reefscape/strategies/cycle_coral.json. Find the rule that should be active while the robot holds CORAL. Follow its trigger and tactic names into common_sim/control/.
  5. Continue the trace into manipulator timing and common_sim/match/match.py. Locate the code that emits the score event. Compare the code path with your timestamped observation.

Expected evidence: you should be able to draw an arrow chain from strategy JSON → selected rule/tactic → navigation/manipulator → deposit event → score. If a piece releases but does not score, record the field location and intended action; a release and a score are deliberately separate decisions.

Turn in: one annotated flow diagram naming the files/functions visited and one explanation of why a robot can release a piece without scoring it.

02Make and test a cycle-time claim

Question: Does a faster drivetrain improve the result enough to matter?

Steps

  1. Before configuring anything, predict the order of results for three PRIMARY speeds: 130, 150, and 170. Write one reason the fastest setting might not win.
  2. Open SWEEP. Add a variable for PRIMARY max_speed with those three values. Use five or more repetitions and enable variability. Without variability, repeated runs are identical copies, not independent evidence.
  3. Keep the strategy and all other robot settings fixed. Check TOTAL RUNS before pressing EXECUTE; write the number in your setup record.
  4. When results complete, compare score, pieces scored, and mean cycle time for each speed. Look for spread within a speed before claiming one speed is better.
  5. Double-click a representative row (not automatically the best row) or use its context menu to replay it in MATCH. Record its seed and one field event that helps explain its result.

Expected evidence: a table/plot that separates an effect of speed from match-to-match noise. “170 had the highest single score” is not enough; state what the repeated rows say.

Turn in: your original prediction, the sweep settings, a chart or small summary table, one replay seed, and a conclusion that includes uncertainty.

03Make a strategy change and hold it out

Question: Can one explainable edit improve a strategy without merely fitting luck?

Steps

  1. Copy an existing strategy JSON to a new filename, such as cycle_coral_lab_name.json. Change exactly one thing: a rule priority, dwell/cooldown, a target action, or the fallback tactic. Write why you expect that change to help.
  2. Load the copy in STRATEGY. Select the rule you changed and use the graph to check its trigger and outgoing behavior. Apply the strategy to PRIMARY, return to MATCH, and RESET.
  3. Run one match only as a debug observation. Pause/scrub near the intended transition. If it did not happen, fix your explanation before running a comparison.
  4. In SWEEP, compare the original and your copy on a first group of seeds. Keep robot, opponent, duration, and variability settings the same for both strategies.
  5. Run a second comparison with different seeds. Call this the held-out check: you may choose your edit using the first set, but the second set judges it honestly.

Expected evidence: the graph/replay confirms the intended transition, and two independent seed sets show whether the result persists. If the first result vanishes on held-out seeds, reject the claim rather than tuning around it.

Turn in: a before/after strategy excerpt, rationale, screenshots or times proving the transition occurred, both seed sets, and one of: keep, reject, or investigate.

04Read a release regression

Question: What must stay stable when we refactor the simulator?

Steps

  1. From the repository root, run python -m apps.run_regression_scenarios. It should report PASS for single_coral_cycle and cycler_vs_defense.
  2. Open game_specific/reefscape/regression_scenarios.py. For each scenario, list its seed, robots, strategies, and protected metrics.
  3. Open test/game_specific/test_reefscape_regression_scenarios.py. Explain why the test uses a real field and strategy JSON in addition to the narrower unit tests.
  4. Imagine a code change changes the first scenario from 40 to 38 blue points. Do not edit the golden value. First reproduce the scenario, replay the match, identify the changed behavior, and decide whether it is an intended model change, a bug, or still unknown.
  5. For a score difference caused only by a broad design comparison, propose a multi-seed SWEEP instead. Fixed-seed regressions protect behavior; they do not prove a strategy is universally best.

Turn in: a mock regression-review comment that cites one protected metric, names the replay evidence you would seek, and states what would justify updating a golden number.
